# 参考项目分析提示词

下面是一整套可直接复用的提示词。后续分析外部参考项目时，直接复制整段给 AI 即可。

```text
待分析项目：

- 项目名称：<填写项目名>
- 仓库地址：<填写仓库地址>
- 相关材料：<项目的说明、介绍推文等>

请先阅读并理解我们项目的产品定位文档：docs/00_PRODUCT.md。

在此基础上，分析上面这个参考项目，并输出一份供我们项目开发使用的参考笔记。

你的任务不是泛泛介绍项目，也不是为了显得全面而强行寻找借鉴点，而是判断：这个项目对我们当前这条产品路线有没有真实参考价值；如果有，主要体现在哪些方面；如果没有或只有局部相关，也要明确写出来。

请始终以 docs/00_PRODUCT.md 和 docs/00_Roadmap.md 作为参考。不要脱离我们自己的产品方向单独评价外部项目。

请特别注意以下要求，并把它们自然落实到最终输出中：

- 必须结合 docs/00_PRODUCT.md 和 docs/00_Roadmap.md 来分析。
- 不要强行寻找借鉴点。
- 只有当某个设计、抽象、边界、工作流、数据模型、运行时机制、服务形态、调度方式、状态管理方式、配置结构，真的和我们当前方向相关时，才写入“可以参考的点”。
- 如果相关性较弱，可以明确写：
  - 参考价值有限
  - 有启发，但当前阶段不适合吸收
  - 更适合作为长期观察对象，而不是近期落地对象
- 不要写空泛赞美，不要写成纯技术盘点，也不要写成学术论文风格。
- 语气要清楚、克制、可读，目标是帮助我们快速判断这个项目是否值得参考，以及该怎么参考。

输出必须严格使用以下结构：

1. 项目介绍
2. 为什么值得我们参考（简析）
3. 可以参考的点
4. 结论

各部分要求如下：

- “项目介绍”：
  简要说明这个项目是什么，它的核心定位、核心能力和工程形态是什么，不要展开成长篇背景介绍。

- “为什么值得我们参考（简析）”：
  重点写它和我们当前方向的关系。说明它为什么和我们有关，或者为什么只有局部相关。这里要结合 docs/00_PRODUCT.md，而不是孤立评价。

- “可以参考的点”：
  只写真正相关的点，宁可少写，也不要凑数。可以适当展开，但必须尽量落在工程抽象、系统边界、任务编排、运行时组织、服务形态、配置模型、状态管理、调度方式、输出结构等层面，而不是泛泛写“值得学习它的架构”。

- “结论”：
  简要总结这个项目是否值得参考，最值得参考的是哪些层面，借鉴的话大致顺序是什么，哪些部分不必借，哪些部分当前阶段不急着吸收。

附加要求：

- 文档开头必须写该项目的仓库地址。
- 如果参考价值有限，也要如实写，不要硬凑“可以参考的点”。
- “可以参考的点”可以稍微详细，但结论必须简洁。
- 如果某个项目明显偏平台、偏 infra、偏部署系统，请特别注意：不要自动把平台能力等同于我们当前阶段必须吸收的能力。
- 如果是第一次分析一个大项目，请优先根据 README、核心设计文档和关键说明材料来判断，不要默认需要通读全部源码。
- 如果你感觉很合适我们，可以多读一读源代码。

```
