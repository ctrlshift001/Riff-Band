# 产品定位说明

## 1. 项目新定位

本项目的定位调整为：

> RiffBand 是一个面向复杂任务执行的轻量级多 Agent 编排引擎，支持 CLI 对话式交互与 MCP 被调用两种形态，并以自动科研任务为特色场景。

宣传语可以是：Riff Band 是一个面向研究任务的即兴 Agent 乐队，能够围绕复杂问题动态编排并创建多个子 Agent，协同完成检索、分析、论证与写作。

这意味着项目不再将自己限定为单一的"产业研究 Agent"，而是将科研能力作为重点优化场景。在产品层面，系统需要同时具备：

- CLI 对话式交互（单 Agent + 多 Agent 模式）
- 动态多 Agent 编排能力（四元组 I/C/T/M）
- MCP 服务模式，可被外部 Agent 调用为编排引擎
- 面向科研任务的固定流程 + 多视角并行能力

## 2. 为什么要调整定位

此前项目更偏向"粤港澳大湾区产业研究 Agent"的垂直场景叙事，这有助于快速形成 demo，但也带来一些限制。

将定位调整为"轻量级多 Agent 编排引擎 + 科研模式"之后，项目会更清晰地分成两层：

- 底层是通用 Agent Runtime / Orchestration System
- 上层是固定流程的研究模式 + MCP 可插拔能力

这样既保留了产业研究方向的展示优势，也为后续拓展到自动科研、知识策展等场景留下空间。

## 3. 核心产品定义

本项目的核心不是一个普通聊天助手，也不是一个固定角色的工作流机器人，而是一个能够根据任务复杂度选择执行模式的 Agent 系统。

产品核心定义如下：

- 对简单任务，提供单 Agent 常规模式
- 对复杂任务，启用动态多 Agent 模式进行拆解与协作
- 对产业研究类任务，提供专门的任务画像、工具包、模型路由和报告输出优化

换句话说，系统既能作为一个通用智能助理使用，也能在复杂任务场景下切换为“多智能体协作执行系统”。

## 4. 两种运行模式

### 4.1 单 Agent 常规模式

该模式面向轻量、直接、低延迟的任务。

适用场景包括：

- 日常问答
- 简单搜索与总结
- 基础文件处理
- 单步或短链路任务

特点：

- 交互简单
- 成本更低
- 响应更快
- 更适合作为默认模式

该模式的目标不是追求复杂编排，而是提供类似通用助手的稳定体验。

### 4.2 动态多 Agent 模式

该模式是系统的特色能力，面向复杂、可拆解、多阶段任务。

适用场景包括：

- 产业研究
- 多维度信息检索与交叉验证
- 多来源证据整合
- 长链路任务执行
- 需要分工协作的复杂问题

特点：

- 由主 Agent 根据任务动态拆解子任务
- 按任务需要为子 Agent 分配 Instruction / Context / Tools / Model
- 支持子任务隔离、并发执行和结果汇总
- 更适合体现系统的编排能力与可扩展性

该模式是项目最核心的差异化能力，也是未来与同类通用 Agent 系统形成区分的关键。

## 5. 产业研究的角色：重点优化场景，而非唯一场景

产业研究依然是当前阶段最重要的落地方向，但其角色发生了变化。

新的理解应当是：

- 产业研究不是系统的唯一目标
- 产业研究是当前最适合深度优化和展示的重点场景
- 它将作为系统能力验证、模式设计和报告输出设计的第一块样板场景

产业研究场景适合本系统，是因为它天然具备以下特征：

- 任务复杂，适合拆解
- 涉及多类信息源
- 需要证据、比较、总结和报告输出
- 很适合验证动态多 Agent 的价值

因此，在产品层面应将产业研究视作“特化 profile”或“重点优化工作流”，而不是将整个系统直接等同于产业研究产品。

## 6. 交互形态：坚持 CLI，不做 GUI

当前产品形态明确为 CLI 工作台，不以 GUI 为主要方向。

这样选择的原因包括：

- 更符合当前项目的工程积累
- 更适合快速迭代 Agent Runtime 与编排能力
- 更容易展示任务执行过程、日志和子 Agent 协作链路
- 更适合开发者、研究者和早期高级用户
- 能将资源集中在系统能力而非前端页面工程上

CLI 应承担的不只是“命令输入”功能，还应承担工作台角色，例如：

- 模式切换
- 任务输入
- Agent 树展示
- 日志与事件流展示
- 工具调用可视化
- 执行状态与结果产物展示

因此，CLI 不应被视为 GUI 的过渡方案，而应被视为本项目在当前阶段的正式产品形态。

## 7. 核心差异化能力

结合新的定位，项目的核心亮点可以概括为以下几点：

### 7.1 双模式执行架构

系统不是默认所有任务都走多 Agent，也不是只能做单 Agent 任务，而是支持根据任务复杂度切换执行模式。

### 7.2 动态多 Agent 编排

相比固定角色型多 Agent 设计，本项目更强调按任务动态创建与配置子 Agent，这使系统具备更强的灵活性与任务适配能力。

### 7.3 四元组驱动的子任务配置

项目延续 I / C / T / M 的思路，用以下四个维度描述一个子任务：

- `I`: Instruction
- `C`: Context
- `T`: Tools
- `M`: Model

这使动态多 Agent 不只是“多开几个角色”，而是“按任务需要合成执行单元”。

### 7.4 对产业研究任务的深度优化空间

通过任务画像、工具包、模型路由、证据记录、报告产出等机制，系统可以对产业研究这类复杂知识工作形成专项优化。

## 8. 当前产业研究 Profile 的实现基础

虽然项目的整体定位已经调整为通用型 Agent 系统，但产业研究依然是当前最成熟、最适合持续打磨的特化场景。现阶段已经沉淀出的实现基础，值得明确保留到产品定义中。

### 8.1 当前已跑通的执行链路

产业研究场景下，当前已经形成一条较完整的执行链路：

`run_agents.py -> build_gba_analysis_project -> MainOrchestratorAgent -> delegate_task/delegate_tasks -> ResearchSubAgent -> Environment/Tools -> complete_task`

这条链路说明，系统并不是停留在概念层，而是已经具备从任务输入、任务拆解、子任务执行、工具调用到最终收尾检查的原型能力。

### 8.2 当前已经实现的产业研究专项能力

围绕产业研究任务，当前已实现的专项能力包括：

- 动态任务委派，支持单任务与批量并行子任务
- 基于任务画像的子任务推断，例如 `policy_research`、`company_research`、`general_research`
- 基于画像的工具包默认分配
- 基于 `model_routing` 的模型路由与回退策略
- 并行执行中的工具安全约束，例如禁止并发阶段直接写报告
- 研究过程留痕，包括 `findings.jsonl` 与运行日志
- 报告最小质量门禁

这些能力说明，“产业研究特化”不是一句定位口号，而是已经开始体现在调度策略、工具设计和结果交付方式上的真实能力。

### 8.3 当前已经具备的工具链

产业研究 profile 下，当前系统已具备一套初步可用的工具链，包括：

- 本地资料检索与读取：`list_sources`、`search_sources`、`read_source`、`read_sources`
- 联网搜索：`web_search`
- 证据记录：`record_finding`
- 报告章节生成：`write_report_section`
- 完成检查：`complete_task`

从产品视角看，这套工具链已经覆盖了产业研究任务最基本的几个环节：

- 找资料
- 读资料
- 记证据
- 写报告
- 过质量门禁

### 8.4 当前并行执行能力的现实意义

当前系统已支持通过 `delegate_tasks` 进行并发子任务执行，并通过环境隔离、输出目录隔离和 findings 合并，尽量避免并发写入冲突。

这一点很重要，因为它说明动态多 Agent 模式并不是纯概念设计，而是已经开始具备真实的并行执行基础。对于产业研究这类天然适合拆分成“政策、公司、产业链、新闻、财务”等子问题的任务来说，这正是后续继续强化的关键能力。

### 8.5 当前质量控制的基础形态

当前系统已经具备基础质量门禁，主要包括：

- 报告文件是否存在且非空
- 二级标题数量下限
- 必要章节是否齐全
- findings 数量是否达到阈值
- findings 证据覆盖率检查
- 报告中是否包含显式链接

虽然这仍然是“规则型最小检查”，但它已经建立了一个重要原则：

> Agent 系统的输出不应只以“生成了结果”为完成标准，还应以“结果是否达到最基本交付要求”为完成标准。

## 9. 当前短板与演进重点

从产业研究 profile 的现状来看，系统已经具备原型能力，但也还有几类问题需要在产品化过程中持续解决：

- 模型路由虽然已支持配置，但多模型分工仍不够充分
- 联网检索能力仍偏单一，缺少更稳的 fallback 与统一检索抽象层
- 工具生态仍以通用检索和读写为主，行业数据连接器不足
- 质量门禁仍偏规则型，缺少一致性校验与证据链校验
- 人机协同能力偏弱，中途审阅、确认和干预机制不足

这些问题并不改变整体方向，反而说明当前的产品演进重点应当是：

- 继续打磨动态多 Agent 的执行质量
- 强化产业研究场景下的证据链与报告能力
- 在保留通用性的前提下，逐步把特化能力做深

## 10. 目标用户

从当前定位出发，目标用户可以分为两类。

### 10.1 核心用户

- 对 Agent 系统和自动化执行感兴趣的开发者
- 希望用 CLI 高效完成复杂任务的高级用户
- 需要可观察、多步骤执行过程的研究者和实验用户

### 10.2 重点场景用户

- 做产业研究与行业分析的用户
- 需要调研、证据整理和报告输出的知识工作者
- 希望用多 Agent 提高复杂任务完成质量的团队

## 11. 产品能力边界

新的定位下，需要明确一些边界，避免目标发散。

当前阶段不追求：

- 图形化 GUI 平台
- 面向大众消费级聊天产品
- 全自动长期自治系统
- 面向所有行业即开即用的完整垂类解决方案

当前阶段重点追求：

- 稳定的通用 Agent 基础能力
- 明确的双模式执行体验
- 可观察、可扩展的动态多 Agent 机制
- 产业研究场景下的高质量任务执行与报告交付

## 12. 结构上的建议

基于新的产品定位，后续架构与目录设计可以围绕三层展开：

- `runtime/orchestration`
  - 通用 Agent Runtime、调度逻辑、上下文管理、工具调用
- `modes`
  - 单 Agent 模式与动态多 Agent 模式的组织层
- `profiles`
  - 产业研究等特化场景的任务模板、工具包、模型路由、报告规范

这样做的目的，是把“系统能力”与“场景优化”分开，避免后续代码继续混在一起。

## 13. 对外表述建议

对外介绍项目时，建议统一使用类似表述：

> RiffBand 是一个面向复杂任务执行的轻量级多 Agent 编排引擎，提供 CLI 对话式交互与 MCP 被调用两种形态，并以自动科研任务为特色场景。

如果需要更短版本，可以使用：

> RiffBand 是一个以 CLI + MCP 为核心交互形态的轻量级多 Agent 编排引擎，重点优化自动科研任务。

## 14. 结论

新的结构应当是：

- 项目本体是轻量级多 Agent 编排引擎
- 动态多 Agent 是核心能力
- 科研模式是重点特色场景（通过 MCP 被外部 Agent 调用时触发）
- CLI + MCP 是主要产品形态

这个定位更利于：

- 产品边界清晰
- 技术路线可持续
- 架构层次更合理
- demo 与长期发展兼容

后续开发中，所有功能设计、目录调整、README 重写和 roadmap 更新，都建议围绕这个新定位统一推进。
