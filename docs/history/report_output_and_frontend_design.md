# 产业研究 Agent 最终报告展示设计说明

## 1. 文档目的

本文档用于总结当前关于“产业研究 Agent 最终报告如何存储、输出以及在网页前端展示”的讨论结论，并给出后续实现过程中的问题提醒与设计建议。

目标是明确一件事：

> 最终成品是网页前端上的完整图文报告页，因此后端输出不能只是一篇纯文本，而应是一套可被前端灵活渲染的结构化报告对象。

## 2. 核心结论

当前最推荐的方案是：

- 后端主存储使用结构化 `report.json`
- Markdown 和 HTML 作为派生导出格式
- 图表、表格、原始数据作为独立资产文件保存
- 前端优先消费结构化 JSON，而不是直接把 Markdown 当唯一数据源

一句话概括：

> 以后端结构化报告对象为核心，以 Markdown/HTML 为导出层，以图表与表格资产为展示素材，由前端完成图文混排和组件化渲染。

## 3. 为什么不能只用纯文本报告

如果后端最终只产出一篇 Markdown 或纯文本，会有几个问题：

- 前端难以做灵活布局
- 图表、表格、引用、摘要卡片等内容不容易组件化渲染
- 不利于局部更新和增量重生成
- 不利于交互式展示
- 后续转 HTML、PDF、可视化页面时扩展成本高

因此，纯文本报告可以保留，但不适合作为唯一主存储格式。

## 4. 推荐的后端输出层次

建议后端输出分为三层。

### 4.1 主存储层：结构化报告对象

这是整个系统最核心的输出，应作为主数据源。

建议形式：

- `report.json`

它需要包含：

- 报告元信息
- 执行摘要
- 章节结构
- 图表定义
- 表格定义
- 引用来源
- 各 SubAgent 结果
- 资产文件路径

这个 JSON 是后续所有渲染和导出的根基。

### 4.2 导出层：人类可读版本

建议保留：

- `report.md`
- `report.html`

作用：

- Markdown 方便调试、存档、版本对比
- HTML 方便做网页快照或导出

但这两者都应由 `report.json` 派生，而不是反过来作为主数据源。

### 4.3 资产层：图表、表格、原始数据

建议独立保存：

- `charts/*.png`
- `charts/*.svg`
- `tables/*.csv`
- `raw/*.json`

这样做的好处：

- 图表有独立文件，前端好引用
- 表格数据可复查
- 原始子任务产物可追溯
- 便于后续重渲染或替换展示方式

## 5. 推荐的目录组织方式

每次报告生成建议使用独立的报告目录，例如：

```text
reports/
  <report_id>/
    report.json
    report.md
    report.html
    assets/
      charts/
        policy_timeline.svg
        funding_trend.png
      tables/
        company_list.csv
        financing_data.csv
      raw/
        policy_research.json
        company_research.json
        news_research.json
```

说明：

- `report.json` 是主入口
- `assets/raw/` 用于保留各 SubAgent 结构化结果
- `charts/` 和 `tables/` 供前端和报告引用

## 6. 前端展示的目标形态

前端最终不应该只是“下载一篇文档”，而应该是一整张可浏览的图文混排产业研究页面。

典型页面结构可以包括：

- 报告标题与主题信息
- 执行摘要
- 核心结论卡片
- 图表与文字分析穿插展示
- 数据表格
- 关键企业信息卡片
- 政策时间线
- 产业链结构图
- 风险提示
- 引用与来源列表

这意味着：

> 前端展示的是“报告页面”，而不是“原样显示一份 markdown 文件”。

## 7. 前端应如何消费后端数据

推荐方式：

- 前端优先读取 `report.json`
- 按 `section type` 分块渲染
- Markdown 只作为某些正文段落的内容格式

也就是说：

- 标题、摘要、图表、表格、结论、引用都应作为独立数据块
- 前端根据块类型调用不同组件

这样才能实现真正的图文混排和高质量展示。

## 8. 建议的 section 设计

建议报告按“内容块”组织，而不是只按“大段长文本”组织。

例如：

```json
{
  "sections": [
    {
      "type": "markdown",
      "title": "执行摘要",
      "content": "..."
    },
    {
      "type": "chart",
      "title": "融资趋势",
      "chart_id": "funding_trend"
    },
    {
      "type": "table",
      "title": "重点企业",
      "table_id": "key_companies"
    },
    {
      "type": "markdown",
      "title": "产业链分析",
      "content": "..."
    }
  ]
}
```

推荐的 section 类型包括：

- `markdown`
- `chart`
- `table`
- `key_findings`
- `timeline`
- `company_cards`
- `citations`
- `risk_notes`

这样前端就可以自由组合布局，而不是被一篇长文档绑死。

## 9. 关于图表的设计结论

我们认为最终报告中加入丰富图表是值得做的，这会显著提升交付物的专业感和产品感。

适合加入图表的内容包括：

- 政策发布时间线
- 融资趋势图
- 重点企业区域分布
- 产业链环节结构图
- 新闻热度变化
- 关键公司对比图

但图表生成必须建立在结构化数据基础上，而不是直接让模型从自然语言“随意画图”。

推荐流程：

1. SubAgent 输出结构化数据
2. 后端使用 Python 库生成图表
3. 图表资产和图表元数据写入报告
4. 前端引用图表或根据配置重新渲染

## 10. 图表实现的潜在问题

图表能力虽然重要，但也存在一些风险。

### 10.1 数据口径不一致

如果多个 SubAgent 获取的数据来源不同、时间范围不同、统计口径不同，就容易出现：

- 正文数字和图表数字不一致
- 图表之间相互矛盾
- 最终结论不可靠

### 10.2 图表语义不正确

不是所有信息都适合画图，常见问题包括：

- 本应用表格表达的信息被误画成图
- 时间序列和分类数据混用
- 图表太复杂，反而降低可读性

### 10.3 运行环境复杂度增加

如果引入：

- `pandas`
- `matplotlib`
- `seaborn`
- `plotly`

会增加依赖管理、环境兼容、字体、渲染与导出复杂度。

尤其是在无头环境下，常见问题包括：

- 中文字体乱码
- 后端渲染失败
- 静态图导出格式不稳定

### 10.4 可追溯性不足

如果图表没有记录：

- 数据来源
- 原始表格
- 生成时间
- 统计口径

后续很难审计和复查。

## 11. 图表能力的建议实现方式

第一阶段建议采用保守、稳定的方案。

推荐：

- `pandas`：处理结构化表格数据
- `matplotlib`：生成稳定静态图
- `seaborn`：补充统计图样式

不建议第一阶段过度依赖复杂前端图表协议或高度自由的自动生成策略。

推荐做法：

- 后端生成静态图 `PNG/SVG`
- 同时保存图表原始数据 `CSV/JSON`
- 若后续需要交互式图表，再增加图表配置对象

## 12. 最终输出格式建议

从当前阶段到未来产品化阶段，推荐的输出策略如下。

### 当前阶段

主输出建议：

- `report.json`
- `report.md`
- `charts/*.png | *.svg`
- `tables/*.csv`

这是最稳、最适合开发和调试的组合。

### 中期阶段

增加：

- `report.html`

适合作为网页报告快照或展示版本。

### 后期阶段

可以考虑：

- PDF 导出
- 交互式图表配置
- 在线协作批注版报告

## 13. 推荐结论

综合当前讨论，最终推荐方案如下：

1. 后端主存储采用结构化 `report.json`
2. Markdown 和 HTML 作为派生导出层
3. 图表、表格、原始数据独立保存为资产文件
4. 前端优先基于 JSON 做组件化渲染
5. 报告按 section block 组织，而不是只输出长文本
6. 图表生成基于结构化数据，不直接从自然语言即兴生成
7. 第一阶段以稳定静态图和可追溯数据为主

一句话总结：

> 最终产品展示应是一张由结构化报告对象驱动的图文混排网页，而不是一篇简单导出的静态文档。

## 14. 对后续实现的建议

如果后续继续推进，建议新增或明确以下能力：

- `ResearchReport` 的 JSON Schema
- 图表元数据 Schema
- section block 的统一定义
- 报告导出器（JSON -> Markdown / HTML）
- 前端 section 渲染组件规范
- 图表与原始数据的可追溯关联机制

这些工作完成后，后端与前端之间的接口会更稳定，也更适合持续迭代。
